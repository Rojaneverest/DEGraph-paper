[TQ10] window-function-impact / medium
Q: The dedup window in `silver/inventory_daily.py` orders by `snapshot_ts` descending. Explain what the descending order achieves, and what the TWO filters in this file do.
Score: None

REFERENCE:
The dedup window is `Window.partitionBy('warehouse_id', 'product_id', 'snapshot_date').orderBy(F.col('snapshot_ts').desc())`, with `row_number()` -> `rn`. The DESCENDING order on snapshot_ts means the most recent (highest snapshot_ts) snapshot within each (warehouse, product, day) gets rank 1 — so the pipeline keeps the LATEST snapshot when the WMS emits multiple snapshots in a single day (e.g. morning baseline + midday recount). The TWO filters: (1) `filter(F.col('rn') == 1)` — the dedup filter, keeping only that latest snapshot per (warehouse_id, product_id, snapshot_date); (2) `filter(F.col('on_hand_units') > 0)` — the empty-stock filter, dropping rows with zero on-hand units (no analytical signal for turnover). Note snapshot_date itself is derived earlier as `to_date(snapshot_ts)` and is the partition key for the dedup window; `utilization_pct = reserved_units / when(on_hand_units==0, None).otherwise(on_hand_units)` is computed before the on_hand>0 filter.

MODEL (google/gemini-2.0-flash-001):
The descending order on `snapshot_ts` in the window function within `silver/inventory_daily.py` ensures that the most recent snapshot is selected when there are multiple snapshots for the same warehouse, product, and date.

1.  `F|D70|D71|rc=rn|pr=F.col('rn') == 1`: This filter keeps only the first row within each window partition, effectively deduplicating the data and retaining only the most recent snapshot based on `snapshot_ts`.

[TQ15] transitive-multi-hop-impact / hard
Q: Trace how `silver.marketing_touchpoints.session_count` feeds into `gold.attribution_funnel_daily`, and point out anything semantically odd about how it is used there.
Score: None

REFERENCE:
In `silver/marketing_touchpoints.py`, `session_count = F.countDistinct('session_id')` per (customer_id, utm_campaign) — the number of distinct sessions a customer had under a campaign. In `gold/attribution_funnel_daily.py`, the `visits` CTE does `COUNT(DISTINCT session_count) AS visit_count FROM marketing_touchpoints GROUP BY utm_campaign, DATE(last_seen_ts)`. So marketing_touchpoints.session_count flows into attribution_funnel_daily.visit_count, which in turn feeds `conversion_rate = purchase_count / NULLIF(visit_count, 0)`. The semantically ODD part: `visits` applies `COUNT(DISTINCT session_count)` — it distinct-counts the session_count value itself (an already-aggregated per-customer count), not the underlying sessions. So visit_count is 'the number of distinct session-count values per campaign-day', which is not a true visit volume — two customers who each had 3 sessions contribute a single distinct value (3). This is a likely modeling quirk/bug worth flagging: the funnel's top-of-funnel 'visit_count' is derived from a distinct count of an aggregate column rather than from raw session or visit counts.

[TQ19] reverse-lineage / hard
Q: `gold.revenue_forecast_features.avg_turnover` is one of the deepest columns in the repo. Trace its full lineage back to bronze, naming each hop.
Score: None

REFERENCE:
`avg_turnover = F.avg('turnover_rate')` in `gold/revenue_forecast_features.py`, where `turnover_rate` comes from the `inventory_turnover_daily` gold table it reads. In `gold/inventory_turnover_daily.py`, `turnover_rate = COALESCE(sold_qty,0)/NULLIF(on_hand_units,0)`. The two inputs split: (numerator) `sold_qty = SUM(quantity)` over `silver.orders_cleaned`, which is built by `silver/orders_cleaned.py` from `bronze.orders_raw` (quantity); (denominator) `on_hand_units` from `silver.inventory_daily`, built by `silver/inventory_daily.py` from `bronze.inventory_snapshots_raw` (on_hand_units passthrough after the latest-per-day dedup). So the hop chain for avg_turnover is: bronze.orders_raw.quantity AND bronze.inventory_snapshots_raw.on_hand_units -> silver.orders_cleaned.quantity / silver.inventory_daily.on_hand_units -> gold.inventory_turnover_daily.turnover_rate -> gold.revenue_forecast_features.avg_turnover. That is 4+ hops (bronze -> silver -> gold turnover -> gold features), and it is gold-reading-gold, which makes revenue_forecast_features the deepest multi-hop node in the benchmark.

[TQ20] producer-consumer / medium

REFERENCE:
