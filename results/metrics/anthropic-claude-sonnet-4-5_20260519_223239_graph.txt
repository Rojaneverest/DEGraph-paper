[Q5] join-chain / hard
Q: In `silver/refunds_enriched.py`, the result joins three bronze tables. List the join keys for each join and explain what happens if `return_id` becomes nullable in `bronze.refunds_raw`.
Score: None

REFERENCE:
Two joins in the file: (1) `refunds_raw` ⨝ `returns_raw` ON `return_id` (inner join), (2) the result ⨝ `orders_raw` ON `order_id` (left join). If `return_id` becomes nullable in `refunds_raw`, the inner join on `return_id` silently drops every refund row with null return_id — silver.refunds_enriched will under-report refund volume. The downstream `refund_ratio = refund_amount / total_amount` derivation cannot compute for those dropped rows. Because the second join is LEFT, the orders side does not introduce additional row loss, but `total_amount` becomes NULL for orphan-order refunds. Net effect: any analytics on refund volume or refund-to-order ratio become biased toward the subset of refunds that arrived with a non-null return_id.

- **Join Keys**: `order_id = order_id`
- **Source**: `refunds_with_return` (result of first join)
- **Right Source**: `orders_df` (from `main.dbdemos_ecom.orders_raw`)
- **Result**: `enriched`

## Impact if `return_id` Becomes Nullable in `refunds_raw`

If `return_id` becomes nullable in `main.dbdemos_ecom.refunds_raw`, the following would occur:

### Immediate Impact:
1. **Rows with NULL `return_id` will be dropped** from the final result because:
   - The first join is an **INNER join** on `return_id`
   - In Spark SQL, `NULL = NULL` evaluates to `NULL` (not `TRUE`), so NULL values never match in join conditions
   - Any refund record with `return_id = NULL` will fail to match any row in `returns_raw` and be excluded

### Data Quality Consequences:
2. **Silent data loss**: Refunds without a valid `return_id` would be silently excluded from `refunds_enriched` with no error or warning

3. **Broken referential integrity**: The pipeline assumes every refund has an associated return (enforced by the INNER join), so NULL values would violate this business rule

4. **Downstream impact**: Any analysis or reporting using `refunds_enriched` would have incomplete refund data

### Recommended Mitigation:
- Add a **data quality check** before the join to validate `return_id IS NOT NULL`
- Consider changing to a **LEFT join** if business logic allows refunds without returns (though this seems unlikely given the domain)
- Add explicit filtering: `refunds_df.filter(col("return_id").isNotNull())` before the join
- Implement monitoring/alerting for NULL `return_id` values in the bronze layer
