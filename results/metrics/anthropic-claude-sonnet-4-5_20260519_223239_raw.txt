Q: In `silver/refunds_enriched.py`, the result joins three bronze tables. List the join keys for each join and explain what happens if `return_id` becomes nullable in `bronze.refunds_raw`.
Score: None

REFERENCE:
Two joins in the file: (1) `refunds_raw` ⨝ `returns_raw` ON `return_id` (inner join), (2) the result ⨝ `orders_raw` ON `order_id` (left join). If `return_id` becomes nullable in `refunds_raw`, the inner join on `return_id` silently drops every refund row with null return_id — silver.refunds_enriched will under-report refund volume. The downstream `refund_ratio = refund_amount / total_amount` derivation cannot compute for those dropped rows. Because the second join is LEFT, the orders side does not introduce additional row loss, but `total_amount` becomes NULL for orphan-order refunds. Net effect: any analytics on refund volume or refund-to-order ratio become biased toward the subset of refunds that arrived with a non-null return_id.

## Impact if `return_id` Becomes Nullable in `bronze.refunds_raw`

If `return_id` becomes nullable in the bronze `refunds_raw` table, the following consequences occur:

### 1. **Rows with NULL `return_id` Are Dropped**
The first join is an **INNER JOIN** on `return_id`. PySpark's join semantics treat NULL as "not equal to anything, including other NULLs." Therefore:
- Any refund row where `return_id IS NULL` will **not match** any row in `returns_raw`
- These rows will be **silently dropped** from the result
- They will never reach the second join or the final silver table

### 2. **Data Loss Without Warning**
The notebook contains no explicit null-handling logic for `return_id`. The comment in section 2 states:

> "The refund→return join is inner: a refund without an RMA is data corruption and should not propagate."

This design assumes `return_id` is always populated. If it becomes nullable:
- **Legitimate refunds** with missing `return_id` (due to upstream data quality issues, schema evolution, or CDC lag) are treated as corruption and discarded
- No row count validation or warning is emitted
- Downstream gold tables (`customer_return_rate`, etc.) will undercount refunds

### 3. **Downstream Metric Distortion**
The silver table feeds into:
- `gold/customer_return_rate.py` (computes `return_rate` from refunds)
- Any ML feature tables that use refund history

If refunds are silently dropped, these metrics become **systematically biased downward**—customers who received refunds with null `return_id` will appear to have lower return rates than reality.

### 4. **Recommended Mitigation**
To handle nullable `return_id` safely, the notebook should:

```python
# Option A: Filter and log nulls before the join
null_return_ids = refunds_df.filter(F.col("return_id").isNull())
null_count = null_return_ids.count()
if null_count > 0:
    print(f"WARNING: {null_count} refunds have NULL return_id and will be dropped")
    # Optionally write to a quarantine table for investigation

refunds_valid = refunds_df.filter(F.col("return_id").isNotNull())
refunds_with_return = refunds_valid.join(returns_df, on="return_id", how="inner")
```

```python
# Option B: Change to LEFT JOIN and handle orphans downstream
refunds_with_return = refunds_df.join(returns_df, on="return_id", how="left")
# Then add a column to flag orphaned refunds:
enriched = enriched.withColumn(
    "has_valid_return",
    F.col("return_id").isNotNull() & F.col("reason_code").isNotNull()
)
```

Option A is safer if null `return_id` truly represents corruption. Option B preserves the data for forensic analysis while flagging it as suspect.
