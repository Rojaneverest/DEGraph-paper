REFERENCE:

The partition key is `claim_id_hdr` (one ranking sequence per claim). The sort is: (1) `diag_priority` ascending, nulls pushed to last — the clinically most significant code (lowest priority number) ranks first; (2) `icd10_code` ascending, nulls last — when two codes share the same priority, the alphabetically earlier ICD-10 code wins. The row numbered 1 becomes `diagnosis_1_code`; rows 2–5 become `diagnosis_2_code` through `diagnosis_5_code`; all codes are also collected into the `other_diagnoses` array<struct>. A sibling procedure-ranking window uses the same pattern with `proc_priority` / `hcpcs_code` and `MAX_PROC=4`.

[Q9] fallback-chain / medium
Q: How is `provider_specialty_code` derived? Describe the full signal-precedence fallback chain from highest to lowest priority, and state what the column value is when no signal fires.
Score: None

REFERENCE:
`provider_specialty_code` is a four-level fallback `when().otherwise()` chain: **(1)** If `coalesce(is_pcp_eligible_reg.cast('boolean'), False) == True` → `'PCP'` (primary rendering NPI is registry-confirmed PCP-eligible); **(2)** Else if `coalesce(any_pcp_flag, 0) == 1` → `'PCP'` (any rendering NPI on the claim is PCP-eligible, broadening the PCP signal beyond the top-ranked provider); **(3)** Else if `specialty_code_reg IS NOT NULL` → `specialty_code_reg` (the NPI+taxonomy-matched specialty code from the provider registry, reflecting the provider's enrolled specialty); **(4)** Else if `rendering_specialty IS NOT NULL` → `rendering_specialty` (the specialty code submitted on the claim by the billing provider — fallback when the registry has no match); **(5)** Otherwise → `NULL`. The two-column LEFT JOIN in the `provider_specialty_df` SQL CTE (joining `ranked_providers` to `bronze.provider_registry` on `rendering_npi = npi AND taxonomy_code = taxonomy_code`) ensures the registry lookup is exact — a provider with multiple taxonomy codes maps to exactly the right specialty row.

MODEL (google/gemini-2.0-flash-001):
