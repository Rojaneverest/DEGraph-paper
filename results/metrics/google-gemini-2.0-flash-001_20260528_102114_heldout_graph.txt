[HQ3] transitive-multi-hop-impact / hard
Q: If `return_qty` in `bronze.returns_raw` becomes nullable, which downstream silver and gold columns become unreliable or are silently dropped? Trace the full impact.
Score: None

REFERENCE:
Three downstream effects, two of which are silent row-loss rather than null-propagation.

(1) `silver/returns_cleaned.py` — applies the filter `.filter(F.col('return_qty') > 0)` immediately before writing. A NULL return_qty fails the `> 0` predicate (PySpark treats `NULL > 0` as UNKNOWN, which is filtered out by `.filter`) — so EVERY null-return_qty row is SILENTLY DROPPED from `silver.returns_cleaned`. Additionally, the derived `is_high_qty = return_qty > F.lit(5)` column becomes NULL for those rows (but they would also be filtered, so unobservable). Result: silver.returns_cleaned silently under-reports returns, biasing downstream counts.

(2) `gold/customer_return_rate.py` — the `returns_agg` CTE computes `SUM(return_qty) AS total_return_qty` from `returns_cleaned`. Because returns_cleaned has already filtered out null-return_qty rows in (1), the SUM is over only non-null rows — the sum value itself is mathematically correct on the surviving rows, but the AGGREGATE IS BIASED LOW because real returns were dropped. `COUNT(return_id) AS total_returns` is similarly biased low. The derived `return_rate = total_returns / total_orders` becomes biased low for every customer who had returns with null qty.

(3) `gold.revenue_forecast_features` — does NOT consume return_qty directly; it inherits from `gold.customer_ltv` which does not use returns data. So no transitive impact through that path.

NOT directly affected: `silver.refunds_enriched` reads `refunds_raw` (refund_amount) and `returns_raw` but uses `return_id` as the join key only — it does NOT reference `return_qty`. So refunds_enriched and `gold.refund_ratio`-equivalent downstream columns are unaffected by return_qty nullability. The marketing/inventory/funnel subgraphs do not touch returns and are unaffected.

[HQ5] join-chain / hard
Q: Inside `silver/customer_profile.py`, describe the full 3-way join chain: which DataFrames are joined, on what keys, with what join types, and what role does the `rename_columns_with_suffix` helper play in keeping the joined columns unambiguous?
Score: None

REFERENCE:
Two sequential PySpark joins build a 3-way result.

Join 1: `co = customers_df.join(orders_df, on='customer_id', how='inner')` — INNER join of `customers_raw` and `orders_raw` on the natural key `customer_id`. The `on='customer_id'` shorthand means the join key appears ONCE in the result (PySpark deduplicates). This is the orders-grain intermediate: one row per (customer, order).

Join 2: `profile = co.join(events_suffixed, co['customer_id'] == events_suffixed['customer_id_last_event'], how='left')` — LEFT join. KEY DIFFERENCE: the right side is `events_suffixed`, NOT the plain `events_latest`. Before the join, `events_latest = events_ranked.filter(F.col('rn') == 1).drop('rn')` was passed through `events_suffixed = rename_columns_with_suffix(events_latest, '_last_event')`. The helper appends `_last_event` to EVERY column name in events_latest, so `customer_id` becomes `customer_id_last_event`, `event_ts` becomes `event_ts_last_event`, etc.

Why the suffix matters: WITHOUT the suffix, the events DataFrame would have `customer_id` as a column — identical name to the column already in `co` from the customers/orders side. The 3-way join result would have TWO `customer_id` columns: an ambiguous-reference bug. Worse, the JOIN CONDITION itself would need disambiguation; PySpark would not know which `customer_id` to use on which side. The suffix renames every column on the events side, so the join condition `co['customer_id'] == events_suffixed['customer_id_last_event']` is unambiguous and the result has `customer_id` (from customers/orders), `customer_id_last_event` (from events), `event_ts_last_event`, and so on. Downstream, the aggregate references `F.max('event_ts_last_event')` — the suffix is what makes that column name reachable.

The helper is registered in `.degraph/helpers.json` as `"kind": "suffix_rename"`, so the extractor emits one explicit Derives edge per renamed column (mapping `name → name + '_last_event'`).

[HQ7] window-function-impact / medium
Q: In `silver/shipments_timeline.py`, the window `Window.partitionBy('order_id').orderBy(F.col('ship_ts').asc())` ranks parcels within an order to produce `shipment_seq`. If the partition key were changed from `order_id` to `customer_id`, what would the new semantic meaning of `shipment_seq` be, and what bug would that introduce in the downstream join with `orders_raw`?
Score: None

REFERENCE:
Current semantics with `partitionBy('order_id')`: `shipment_seq` is the within-order parcel sequence number ordered by ship timestamp ascending. For an order shipped as 3 parcels at times t1 < t2 < t3, shipment_seq is 1, 2, 3 respectively. The downstream aggregate then computes per-order summaries (shipment_count, first_ship_ts, last_delivered_ts, carriers_used), and the inner join with `orders_raw.select('order_id', 'customer_id')` attaches `customer_id` per order. shipment_seq itself is NOT in the final write (the aggregate produces shipment_count instead) — it is a within-order helper rank.

If the partition were changed to `partitionBy('customer_id')`: shipment_seq would become the per-CUSTOMER parcel sequence number — i.e. the Nth parcel ever shipped to that customer across ALL their orders. A customer with 3 orders of 2 parcels each would see shipment_seq running 1..6 across all six parcels in ship_ts order, regardless of order boundaries.

The downstream bug: the `.groupBy('order_id')` aggregate would still produce per-order aggregates (shipment_count, first_ship_ts, etc.) correctly — the aggregate doesn't depend on shipment_seq because shipment_seq is dropped at the aggregate (only count, min, max, collect_set are computed). So the WRITTEN silver columns would be unchanged. The functional impact is that any DOWNSTREAM file that referenced `shipment_seq` would now see customer-level ranks instead of order-level ranks; but in this benchmark NO downstream file references shipment_seq (it does not appear in any other file). Therefore the change would be silently incorrect for any analyst reading `shipments_seq` as an intermediate, but invisible to the current silver/gold pipeline.

A second, less obvious bug: customer_id is not present on shipments_raw directly (the file does NOT have customer_id on shipments_seq); the join with orders_raw to bring in customer_id happens AFTER the window. So `partitionBy('customer_id')` would fail at extraction time with a 'column not found' error on `shipments_seq.customer_id`. To actually make that change work, you would also have to move the orders_raw join BEFORE the window — restructuring the file.

MODEL (google/gemini-2.0-flash-001):

Q: Describe the `DeltaMergeSink` class in `utils/sinks.py`: what constructor kwargs does it take, what does its `run(df)` method do, how does DEGraph recognize call sites that use it (registered vs heuristic-fallback), and what would happen if the class were NOT registered?
Score: None

REFERENCE:
Class definition (`utils/sinks.py`): `class DeltaMergeSink` with `__init__(self, target_table: str, merge_keys: List[str], mode: str = 'merge', update_condition: Optional[str] = None)` — four constructor parameters: target_table (the FQN string), merge_keys (the list of columns to merge on), mode (default 'merge'), and update_condition (optional SQL fragment for `whenMatchedUpdate`'s condition).

`run(df)` method behavior: (1) Get the active Spark session. (2) If the target table does NOT exist, fall back to `df.write.format('delta').saveAsTable(target_table)` and return — the first-write path is a plain CREATE. (3) Otherwise, get the Delta target via `DeltaTable.forName(spark, target_table)`, build a merge condition as `' AND '.join(f't.{k} = s.{k}' for k in merge_keys)`, alias target as `t` and source df as `s`, call `whenMatchedUpdateAll(...)` (with the optional update_condition if provided), then `whenNotMatchedInsertAll().execute()`. Net effect: SCD-Type-1 upsert.

DEGraph recognition (per `dev/methodology.md` Decision 3.8): two-tier mechanism. Tier 1 (preferred, used here): the class is REGISTERED in `.degraph/sinks.json` which maps `DeltaMergeSink` to `target_table` kwarg → table FQN and `mode` kwarg → write mode (default 'merge'). Because it is registered, the extractor recognizes a bare `DeltaMergeSink(target_table=..., merge_keys=[...]).run(df)` call site (no `.write`, no `saveAsTable`) as a proper WritesEdge with `sink_class='DeltaMergeSink'`, `mode='merge'`, and the merge_keys captured.

If NOT registered (tier 2 heuristic fallback): the extractor would still detect it because the class name matches the `*Sink`/`*Writer` heuristic AND has a kwarg in `{target_table, target, sink_table}`. A WritesEdge would still be emitted but with `mode='<unresolved>'` AND a `GraphWarning` of kind `unregistered-custom-sink` would be added. This benchmark exercises path 1 (registered) — no such warning is in the graph. If the registration were removed AND the heuristic didn't fire (e.g. the class were named without the Sink/Writer suffix), the write would be SILENTLY DROPPED — which is the single worst failure mode for a lineage tool and the reason the heuristic exists as a backstop.

[HQ10] coverage-of-unknowns / medium
Q: How does DEGraph distinguish a *registered-passthrough* opaque call (like `trim_string_columns`) from an *unregistered-opaque* call (like `utils.event_parsers.parse_event_payload`)? Where does the registration live, what does it mean for the emitted edge, and what is the impact-analysis consequence of the distinction?
Score: None

REFERENCE:
Both kinds of calls — wrappers like `trim_string_columns(df)` and `parse_event_payload(df)` — are AST-level opaque to the extractor: the function body is in another file and the extractor does not inline-execute Python. DEGraph distinguishes them via a registry file: `.degraph/helpers.json`. Each entry maps a fully qualified helper name to a `kind` field. The two relevant kinds here:

(1) `"kind": "passthrough"` — declares that the helper preserves the input DataFrame's column set (values may change, schema does not). Example: `trim_string_columns` in `utils.column_transformations`, used in both `silver/orders_cleaned.py` and `silver/returns_cleaned.py`. The extractor emits an `OpaqueTransform` edge with `is_passthrough=true` and `opaque_kind='passthrough'`. The DataFrame node produced by the call has the SAME column set as the input. Downstream column-set reasoning treats the call as transparent — column-level impact analysis traces THROUGH the passthrough as if it were an identity transformation.

(2) `"kind": "suffix_rename"` — declares that the helper renames every column by appending a suffix; the extractor emits one DerivesEdge per renamed column (mapping `name → name + suffix`). Example: `rename_columns_with_suffix` in `utils.column_transformations`, used in `silver/customer_profile.py`. Different from passthrough because the column set CHANGES (columns are renamed, not preserved).

Unregistered: if a helper is NOT in `.degraph/helpers.json` (or `.degraph/helpers.json` doesn't exist or doesn't contain that name), the extractor falls back to emitting an `OpaqueTransform` edge with `is_passthrough=false` and `opaque_kind='unknown'`. Example: `utils.event_parsers.parse_event_payload` in `bronze/03_ingest_events.py` — the function strips `payload` and adds `page_url`, `referrer`, `user_agent`, `cart_total`, but DEGraph cannot know that statically because the helper is not registered. The extractor emits a `GraphWarning` of category `opaque-call-fallback` (per tuning-Q10) AND the OpaqueTransform edge marks the column-set change as opaque — downstream column-level impact analysis CANNOT trace through this call.

Impact-analysis consequence: a registered passthrough means a question like 'if column X is renamed, which downstream tables are affected?' can correctly count the downstream silver tables; an unregistered opaque means the analysis stops at the opaque boundary — downstream effects are reported as 'unknown'. The cost of unregistered helpers is reduced column-level resolution at exactly the file boundaries where domain logic lives.

MODEL (google/gemini-2.0-flash-001):
DEGraph distinguishes a registered-passthrough opaque call from an unregistered-opaque call based on the presence of the `pass` keyword in the `@EDGES` section for the opaque transformation (`O`).

- **Registered-passthrough opaque call:** The `pass` keyword is present in the `@EDGES` entry. This indicates that the function being called is known to not change the column set of the DataFrame. An example is `O|D82|D82|utils.column_transformations.trim_string_columns|pass`.
- **Unregistered-opaque call:** The `pass` keyword is absent in the `@EDGES` entry. This indicates that the function being called is not registered as a passthrough function, and DEGraph cannot determine if the column set changes. An example is `O|D7|D8|utils.event_parsers.parse_event_payload`.

The registration of passthrough functions is not explicitly shown in the provided DEGraph DSL. It would likely live within the code of the DEGraph tool itself, where certain functions are pre-defined or configured as column-set-preserving transformations.

**Impact-analysis consequence:**

- For registered-passthrough calls, removing the opaque transform will *never* change the column set.
- For unregistered-opaque calls, removing the opaque transform *might* change the column set. DEGraph emits a `@WARN` entry to highlight this uncertainty. This means impact analysis must consider the possibility of column set changes when reasoning about the effects of removing the transform.
