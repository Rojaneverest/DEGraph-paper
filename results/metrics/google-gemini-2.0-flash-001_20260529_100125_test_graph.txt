[TQ13] custom-sink / medium
Q: Based on the body of `DeltaMergeSink.run()` in `utils/sinks.py`, what does the sink do on the very first run (when the target table does not yet exist) versus on subsequent runs, and what columns/keys drive the merge?
Score: None

REFERENCE:
`DeltaMergeSink.run(df)` branches on whether the target already exists: `if not spark.catalog.tableExists(self.target_table): df.write.format("delta").saveAsTable(self.target_table); return`. So on the FIRST run (table absent) it simply creates the table with a plain Delta `saveAsTable` — no merge. On SUBSEQUENT runs (table exists) it performs a MERGE: `target = DeltaTable.forName(spark, self.target_table)`, builds the match condition by joining the merge keys (`" AND ".join(f"t.{k} = s.{k}" for k in self.merge_keys)`), then `target.alias("t").merge(df.alias("s"), condition).whenMatchedUpdateAll().whenNotMatchedInsertAll().execute()` — i.e. update matched rows in place and insert new ones (SCD-Type-1 upsert). An optional `update_condition` (default None) can gate the `whenMatchedUpdateAll`. For `gold/product_performance.py` the merge keys are `["product_id", "order_date"]`, so matching is on `t.product_id = s.product_id AND t.order_date = s.order_date`.

[TQ20] reverse-lineage / medium
Q: Trace the inputs of `gold.customer_ltv.days_since_last_order` back through the pipeline, and identify any source of non-determinism in its value.
Score: None

REFERENCE:
`days_since_last_order` is computed in `gold/customer_ltv.py`'s `ranked` CTE as `DATEDIFF(CURRENT_DATE(), b.last_order_ts) AS days_since_last_order`. Its inputs: `last_order_ts` comes from the `base` CTE, which selects it from `main.dbdemos_ecom.customer_profile`. In `silver/customer_profile.py`, `last_order_ts = F.max("order_ts")` over each customer's joined orders; `order_ts` is a bronze `orders_raw` column (read directly by customer_profile), ingested by `bronze/01_ingest_orders.py`. So the data chain is: `bronze orders_raw.order_ts` -> `customer_profile.last_order_ts = max(order_ts)` -> `customer_ltv.days_since_last_order = DATEDIFF(CURRENT_DATE(), last_order_ts)`. Non-determinism: the `CURRENT_DATE()` term makes the value depend on the DATE THE JOB RUNS — the same input data yields a different `days_since_last_order` on different run dates. This is a run-time-dependent (non-reproducible across days) column, unlike the purely data-derived columns around it.

MODEL (google/gemini-2.0-flash-001):
`T5.days_since_last_order` is derived from `D12.days_since_last_order`.
`D12` is the result of a join between `D10` and `D11`.
`D10` is read from `T4`.
`D11` is the result of an aggregation on `D10` grouped by `country_code`, calculating `avg_country_ltv`.
`T4` is derived from `T0`, `T1`, and `T3`.

Specifically, `T4.last_order_ts` is an input to `T5.days_since_last_order` via `T4`, `D10`, `D12`, `D13`, `D14`, and `T5`.
`T4.last_order_ts` is an aggregate of `T0.order_ts`.
`T0.order_ts` is a passthrough from the external source `/Volumes/main/dbdemos_ecom/landing/orders.order_ts`.

Non-determinism:
